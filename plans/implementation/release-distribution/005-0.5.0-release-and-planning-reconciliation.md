Status: active

## 1. Objective

Prepare, qualify, and manually publish StegoEggo 0.5.0 as the next ordinary stable
release after 0.4.2, while reconciling the planning state created by the completed
Stego Library Evolution M001–M005/M008 work.

0.5.0 is intentionally the shared live release event for:

1. the first ordinary Eggpack-produced stable CLI release after the producer cutover;
2. the real public 0.4.2 → 0.5.0 native updater transition required by Plan 106 /
   Release-Distribution M001;
3. the remaining live-release evidence required to fully close
   Release-Distribution M002;
4. publication of the generic carrier/API/resource/WebP work completed since 0.4.2.

Release-Distribution M004 selected 0.4.3 as a patch release but correctly stopped before publication when `cargo semver-checks` found new variants on stable public enums relative to crates.io 0.4.2. The maintainer has selected 0.5.0, the next 0.x minor release, for those already-landed stable API additions. This milestone does not authorize keyed carrier placement. Stego Library Evolution M006
remains blocked solely on ADR-0007 acceptance.

## 2. Why this milestone is ready

The current mainline is green after Stego Library Evolution M008. M008 corrected the
M003 compatibility issue before any stable release newer than 0.4.2, so the post-0.4.2
carrier work is now suitable for release qualification.

The repository's latest GitHub stable release is still v0.4.2. Release-Distribution
M001 and the remaining condition on M002 both explicitly require the next ordinary
stable B newer than 0.4.2; the maintainer has selected 0.5.0 for that release.

Before mutating versions, the implementation MUST verify that 0.5.0 is unused for all
three publishable crates and that no public v0.5.0 tag/release already exists. If any
0.5.0 publication is already consumed, stop rather than silently selecting another
version.

## 3. Release contents and current evidence

The 0.5.0 source release includes, at minimum, the already-closed work since v0.4.2:

- Stego Library Evolution M001 metadata-write boundary convergence.
- M002 generic JPEG API normalization with explicit best-effort naming.
- M003 carrier-owned `CarrierLimits` and prepared-JPEG hardening.
- Stego Library Evolution M004 transactional tiled in-place allocation hardening.
- Stego Library Evolution M005 opt-in still-lossless WebP byte carrier facade.
- M008 restoration of the v0.4.2 JPEG compatibility domain while retaining explicit
  bounded APIs.
- Maintenance Quality M001 release/binding workflow consolidation and immutable action
  pinning.
- Previously closed binding/API/verification work present on main after v0.4.2.

The exact release notes MUST be generated from `git log v0.4.2..HEAD` and the closure
records rather than copied from this summary. Root and carrier semver checks MUST pass
for the selected 0.5.0 version before publication; the added enum variants were the
reason the 0.4.3 patch candidate was stopped. Do not claim an unreleased or merely
proposed capability.

## 4. Invariants that must not regress

- Versions of `stegoeggo-stego`, `stegoeggo`, and `stegoeggo-cli` remain
  lockstep and exact path dependency requirements become `=0.5.0`.
- crates.io publication remains manual and ordered carrier → library → CLI.
- crates.io remains the CLI updater's stable-version authority.
- The GitHub v0.5.0 tag points exactly to the qualified release source and is never
  force-moved.
- The Eggpack-generated five-target binary workflow remains byte-drift checked.
- The GitHub release is staged as a draft and published explicitly by a maintainer.
- The 15-file Eggpack asset contract remains unchanged.
- No release automation gains crates.io, PyPI, or npm publication credentials.
- M008's legacy-vs-bounded carrier behavior remains intact.
- Existing carrier known-answer vectors, seed mappings, metadata bytes, C ABI 1.0
  contract, and CLI updater policy remain unchanged.
- Python/Node/C source package versions track 0.5.0, but registry publication for those
  bindings remains separate/manual and is not authorized by this milestone.
- ADR-0007 remains proposed unless separately accepted; M006 keyed placement is not part
  of 0.5.0.

## 8. Failure, partial-publication, and recovery semantics

crates.io versions are immutable. Follow the existing partial-publication policy:

- if carrier 0.5.0 publishes and root cannot be published from the exact qualified
  source, stop and assess whether the remaining packages can safely use 0.5.0;
- if a source correction changes an already-published package's bytes/contract, do not
  overwrite or yank-and-reuse 0.5.0;
- select a new version only through a new maintainer decision/plan.

If binary staging fails, leave the GitHub release draft unpublished and retain evidence
for diagnosis. Reruns may reconcile exact matching assets but must fail closed on
same-name/different-byte collisions.

Do not present 0.5.0 as updater-ready until the complete required public asset set is
attached and the GitHub release is published.

## 9. Compatibility and migration

0.5.0 is the next 0.x minor compatibility boundary after 0.4.2. Under the
repository's pre-1.0 version policy, API-breaking changes may ship only on a minor
version increment; patch releases remain API compatible. `FieldSource::Unavailable`
and `VerificationResult::Invalid` are stable enum additions already present on main.
Rust callers that exhaustively match either enum may need to add arms when moving to
0.5.0. Other callers require no migration. No carrier payload, metadata, C ABI, or
updater policy format changes are included.

The release preserves M008's JPEG compatibility domain and existing carrier
known-answer behavior. Explicit bounded carrier APIs remain recommended for untrusted
generic inputs, while legacy JPEG entry points retain their historical effective domain.

Binding source versions move to 0.5.0 for repository consistency. This milestone does
not imply PyPI/npm publication and does not change C ABI 1.0.

## 13. Acceptance criteria

M005 closes only when:

1. 0.5.0 was confirmed unused before publication;
2. all core/source binding version metadata is internally consistent;
3. release-prep CI and required local qualification are green;
4. `stegoeggo-stego`, `stegoeggo`, and `stegoeggo-cli` 0.5.0 are public on

   published;

## 14. Stop conditions

Stop rather than improvising if:

- any 0.5.0 core crate version or GitHub v0.5.0 tag is already consumed;
- a required pre-release test or release-contract check is red;
- package contents unexpectedly expose private carrier internals or omit required docs;
- semver evidence finds a public API break not already explicitly accepted;
- M008 compatibility fixtures regress;
- Eggpack-generated workflow drift is nonzero;
- a native binary fails identity/version/GLIBC/smoke qualification;
- the asset inventory differs from the exact contract;
- crates.io and GitHub release identities disagree;
- updater 0.4.2 resolves anything other than stable 0.5.0 after publication;
- a partial immutable publication requires changed bytes.

No stop condition authorizes silently skipping evidence or substituting a prerelease.
