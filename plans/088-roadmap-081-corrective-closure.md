## Verified closure gaps

### 1. Timestamp-dependent JPEG convergence flake

`tests/request_aux_convergence.rs::sync_variants_agree_jpeg` has been observed to fail when two semantically equivalent canonical calls straddle a wall-clock second boundary. The source of nondeterminism is the structured JPEG COM marker timestamp generated by `generate_structured_com_marker` in `src/protected/metadata_trap/notice.rs`, which currently uses `SystemTime::now()` rather than the request's deterministic timestamp context.

Plan 085 records local reproduction of the failure and a CI rerun that passed after the initial failure. This must be eliminated before Roadmap 081 is considered fully closed.

### 2. Plan 083 status ledger is stale

The status must be updated only after re-validating the implementation against current `main`.

### 3. Roadmap 081 status ledger is stale

## Scope

### A. Make structured-marker timestamps deterministic under canonical requests

1. Trace the timestamp provenance used by metadata/notice generation in the canonical request pipeline.
2. Ensure structured JPEG COM marker generation uses the same resolved/request timestamp source already used elsewhere for deterministic protection output, including `ProtectionRequest::with_timestamp_override(...)` / resolved execution context.
3. Do not globally freeze timestamps or change default production semantics: when no override is supplied, normal execution should continue to use the current time as defined by the existing request/plan semantics.
4. Prefer passing an already-resolved timestamp into the marker renderer over adding another direct wall-clock read in a lower-level helper.
5. Keep serialized marker grammar and timestamp format unchanged except for correcting the provenance of the timestamp value.
6. Audit sibling PNG/WebP/XMP/notice renderers for direct time reads that could defeat request-level determinism. Fix only equivalent provenance violations found during this audit; do not broaden into unrelated metadata refactoring.

### B. Add regression coverage for deterministic equivalence

Add or tighten tests proving that repeated canonical processing with identical bytes and an explicit timestamp override produces byte-identical output for JPEG, including structured COM metadata.

Required regression coverage:

- same input + same request + explicit timestamp override => byte-identical JPEG output across repeated calls;
- `process_request_bytes`, `process_request_bytes_with_warnings`, and `process_request_bytes_with_report` remain byte-equivalent for the same deterministic request;
- the test remains stable across an intentional wall-clock delay or a loop sufficient to cross second boundaries;
- PNG/WebP deterministic equivalence remains green;
- no behavior change when no timestamp override is supplied, beyond removal of inconsistent lower-level time reads.

Avoid sleep-heavy tests if possible. Prefer a test seam or repeated execution whose correctness does not depend on timing luck.
